dev-agent is a headless, autonomous web-app builder. Hand it a product description and it scopes, plans, builds, verifies, and deploys the app — unattended, with a deterministic gate after every step. Hand it a bigger PRD and it designs a multi-service system and builds every service the same way. This deck explains what it is and how to use it.

dev-agent · how it works01 / 11
◢ dev-agentthe core idea

the core idea

LLM brain, deterministic hands.

The model decides what to build. Plain Python owns how the run proceeds — the sequence of phases, the budget ceilings, and a hard pass/fail gate after each one. The build's own claim of "it worked" is never trusted: a gate re-checks the real artifact on disk.

PRD ─▶ scope ─▶ plan ─▶ build ─▶ verify ─▶ deploy ─▶ preview + report └──── fail any gate, the run stops and says why ────┘

Modules that call Claude: scope, plan, and the build executor. Everything else — orchestrator, budget, ledger, gates, sandbox, verifier, egress — runs no model at all.

dev-agent · how it works02 / 11
◢ dev-agentthe pipeline

the pipeline

Five phases, a gate after each.

phasewhat it doesgate
scopeClassifies any request into a confirmed ProjectScope — deliverable type(s), stack, storage. Asks clarifying questions if ambiguous.recipe known
planBreaks the scope into tasks; each task owns a disjoint set of files so parallel build agents never collide.file owners disjoint
buildThe executor writes the app and runs the real toolchain build. A repair loop (cap 2) feeds failures back in.bundle exists
verifyRebuilds from source in a clean container, boots the app, runs the spec's machine-checkable acceptance checks.build + checks green
deployServes the build from a preview container on the host and proves the URL actually answers.HTTP 200

The orchestrator stays dumb: one pass per phase, stop on a red gate or a budget breach. A gate is pure pass/fail code over the artifact — never the model's self-assessment. In a system build, this exact pipeline runs once per service.

dev-agent · how it works05 / 11
◢ dev-agentwhat it builds

scope-first

The request decides the shape.

The scope phase reads the PRD and picks the deliverable — it isn't locked to one kind of app. Each scope type maps to a recipe that provisions the right toolchain; the registry is open, so new targets drop in without touching the pipeline.

frontend
node-vite-react
A Vite + React + Tailwind SPA, served as a static bundle.
backend
node-express
An Express API, booted and probed with real HTTP + JSON checks.
fullstack
api + web
Both at once in a monorepo, built and verified target-by-target.

Storage is the agent's per-PRD decision: none, in-process SQLite, or a managed Postgres / Mongo datastore — chosen by the scope model, never by an operator flag. A PRD that needs several services escalates to the system level — next slide.

the new ability · build-system

One PRD in. A system of services out.

01

PRD → service DAG + contracts
02
build tree
full pipeline per service
03
bring up
per-run docker network

cross-service E2E
  • The Architect designs, a gate re-checks. The model emits a SystemDesign — services (api, web, db…), a dependency DAG, and the contracts between them (OpenAPI, db schema, auth). Deterministic code re-validates all of it: known stacks, resolvable dependencies, acyclic, contracts consistent.
  • Every service gets the whole five-phase pipeline as its own sub-build — in dependency order, independent siblings concurrently — under one shared, thread-safe budget. A failed service blocks only its dependents; the rest still build.

dev-agent · how it works08 / 11
◢ dev-agenttrust model

why you can trust it

Verify doesn't trust the build.

  • Rebuild from source in a clean container, with no API key — rm -rf dist && pnpm install --frozen-lockfile && pnpm build. A stale, drifted, or hand-faked bundle can't survive this.
  • Boot the real app and exercise it — HTTP status codes, JSON response bodies, and rendered DOM selectors. The model isn't asked whether it worked; the checks compute a verdict.
  • Persistence is proven, not promised: if the scope picked a datastore, verify writes a record, restarts the app while the store stays up, and reads it back — so the state truly lives in storage, not memory.

The executor's own success claim is ignored everywhere — the gate, not the model, is the oracle. At the system level too: the architect's design, each service's build, and the cross-service E2E each face their own deterministic gate.

dev-agent · how it works09 / 11
◢ dev-agentcontainment

how it stays contained

Disposable, secret-safe, deny-by-default.

disposable
docker run --rm
Every build runs in a throwaway non-root container. Nothing persists between runs but the app under runs/<id>/out/.
secret hygiene
key by env name
The API key is passed by environment name, never on the command line — and verify and deploy carry no key at all.
egress allowlist
api + npm only
Build and verify sit on an internal network behind a CONNECT proxy that permits only api.anthropic.com and the npm registry. Everything else is refused.

The deterministic spine that holds the model in: orchestrator (one pass per phase), budget (hard token / cost / time ceilings — one budget spans every concurrent sub-build of a system run), ledger (an append-only JSONL audit trail), and the gates.

dev-agent 是一个无人值守的自主 Web 应用构建器。给它一份产品描述，它会自动完成需求界定、任务规划、编码构建、验证与部署——每一步之后都有一道确定性的闸门。给它一份更大的 PRD，它会自行设计出一个多服务系统，并用同样的方式构建每个服务。本文档介绍它是什么、怎么用。

dev-agent · 工作原理01 / 11
◢ dev-agent核心理念

核心理念

LLM 是大脑，确定性代码是双手。

模型决定造什么；纯 Python 掌控流程怎么走——阶段顺序、预算上限、以及每个阶段之后一道硬性的通过/失败闸门。构建过程自己说"成功了"从不被采信：闸门会重新检查磁盘上的真实产物。

PRD ─▶ scope ─▶ plan ─▶ build ─▶ verify ─▶ deploy ─▶ 预览 + 报告 └──── 任何一道闸门失败，运行立即停止并说明原因 ────┘

会调用 Claude 的模块：scope、plan、以及 build 执行器。其余一切——编排器、预算、账本、闸门、沙箱、验证器、出网代理——完全不跑模型。

dev-agent · 工作原理02 / 11
◢ dev-agent流水线

流水线

五个阶段，每段之后一道闸门。

阶段做什么闸门
scope把任意请求归类为一份确认过的 ProjectScope——交付物类型、技术栈、存储方案；有歧义时会先提出澄清问题。recipe 已注册
plan把 scope 拆成任务；每个任务独占一组互不重叠的文件，并行构建的 agent 之间永不冲突。文件所有权不相交
build执行器编写应用并跑真实的工具链构建；修复循环（上限 2 次）把失败信息喂回去。产物存在
verify在干净容器里从源码重新构建、启动应用、执行规格中机器可查的验收检查。构建 + 检查全绿
deploy用预览容器在宿主机上提供服务，并证明 URL 真的有响应。HTTP 200

编排器保持"笨"：每个阶段只跑一遍，闸门变红或预算超限即停。闸门是对产物的纯 pass/fail 代码——绝不采用模型的自我评价。在系统级构建中，同一条流水线会对每个服务各跑一次。

◢ dev-agent构建目标

scope 优先

需求决定形态。

scope 阶段读 PRD 并选定交付物——它不锁死在某一种应用形态。每种 scope 类型对应一个 recipe，负责准备正确的工具链；注册表是开放的，新目标类型可以直接加入而不动流水线。

前端
node-vite-react

后端

全栈

Monorepo 中两者兼有，逐目标构建、逐目标验证。

存储方案由 agent 按 PRD 自行决定：不用存储、进程内 SQLite、或托管 Postgres / Mongo 数据库——由 scope 模型选择，绝不靠操作员开关。需要多个服务的 PRD 会升级到系统级——见下一页。

dev-agent · 工作原理08 / 11
◢ dev-agent信任模型

为什么可以信任它

Verify 不信任 Build。

  • 在干净容器里从源码重建，不带 API key——rm -rf dist && pnpm install --frozen-lockfile && pnpm build。过期的、漂移的、或手工伪造的产物都过不了这一关。
  • 真实启动应用并实际调用它——HTTP 状态码、JSON 响应体、渲染后的 DOM 选择器。不问模型"成功了吗"；由检查计算出判定。
  • 持久化靠证明，不靠承诺：如果 scope 选了数据库，verify 会写入一条记录、在数据库保持运行的同时重启应用、再把它读回来——状态确实存在存储里，而不是内存里。

执行器自己的 success 声明在任何地方都被忽略——判定者是闸门，不是模型。系统级同理：architect 的设计、每个服务的构建、跨服务 E2E，各自面对自己的确定性闸门。

dev-agent · 工作原理09 / 11
◢ dev-agent隔离与约束

如何保持受控

用完即弃、密钥安全、默认拒绝。

用完即弃
docker run --rm
每次构建都在一次性的非 root 容器里进行。除 runs/<id>/out/ 下的应用外，运行之间不留任何东西。
密钥卫生
按环境变量名传递
API key 只按环境变量名传入，从不出现在命令行——verify 和 deploy 则完全不携带任何 key。
出网白名单
仅 api + npm
build 和 verify 位于内部网络，经 CONNECT 代理只放行 api.anthropic.com 和 npm 仓库，其余一律拒绝。

约束模型的确定性脊柱：编排器（每阶段一遍）、预算（token / 费用 / 时间硬上限——系统级运行的所有并发子构建共享同一份预算）、账本（只追加的 JSONL 审计流）、以及闸门。
